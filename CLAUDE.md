# RouteBridge: notes for Claude

Last-mile delivery platform for Nigeria. FastAPI backend, Next.js console, offline driver PWA. Product spec: `project description.md`. Setup and
overview for people: `README.md`. This file holds what is NOT obvious from the code.

## Layout
- `backend/apps/api/src/routebridge/` API: `routes/` (HTTP), `services/` (logic), `models/` (SQLModel tables), `auth/` (Clerk + roles),
  `workers/` (outbox, notifications), `tools/` (migrate, gen_secrets, send_test_sms). Migrations: `backend/apps/api/alembic/versions/`.
- `frontend/routebridge/apps/web/` Next.js 14 (App Router, `output: 'standalone'`). `components/` screens, `lib/` api client and logic.
  Console pages (`/orders`, `/dispatch`, ...) all re-export `app/page.tsx`, which picks the view from the URL.
- `backend/tests/` pytest. `design-system/routebridge/` design tokens and the logo.

## Run and verify (Windows, this machine)
- Whole stack in Docker: `docker compose up -d --build` from the project root (see README). Kubernetes/Terraform were removed on purpose: Docker Desktop only.
- API (without Docker): from `backend/apps/api`, `PYTHONPATH=src .venv/Scripts/python -m uvicorn routebridge.main:app --port 8000`; migrations with
  `python -m routebridge.tools.migrate` (idempotent, locked). Real Postgres on `localhost:5433`, Redis, MinIO; config in `backend/apps/api/.env`.
- **This shell has `ROUTEBRIDGE_DATABASE_URL` set to the REAL Postgres.** Always run pytest as `ROUTEBRIDGE_DATABASE_URL=sqlite:///scratch_test.db PYTHONPATH=... pytest` (relative path; a `/c/...` path fails). One unprefixed run already created a stray empty `billingpayment` table in the real database (migration `e5f6a7b8c9d0` drops such a leftover).
- Tests: from `backend/`, `PYTHONPATH=apps/api/src apps/api/.venv/Scripts/python -m pytest tests -q`. SQLite by default. Never point the suite at the
  real database: it empties tenants. Use a scratch database. Delete stray `routebridge.db` files tests leave in `backend/`.
- Web: from `frontend/routebridge/apps/web`: `npx tsc --noEmit`, `npx next lint`, `npx vitest run`. Serve with `next build`, then copy `.next/static` and
  `public` into `.next/standalone/` and start `node .next/standalone/server.js` with `HOSTNAME=0.0.0.0 PORT=3000`. Open `http://localhost:3000`
  (the API only allows that origin). Stop any running server before rebuilding. The build takes about 10 minutes on OneDrive: run it in the background.
- A green `tsc` is NOT proof a UI change landed (an edit once compiled but rendered nothing). Check the screen or a Playwright screenshot.

## Rules that matter
- **Secrets:** `.env` and `.env.local` hold real Clerk and SMS keys. Never print or commit them; read them in code, not into the chat.
- **Real data:** the owner's real workspace ("RouteBridge Operations") lives in the dev database. Before any browser or data test, check what exists.
  Use clearly named test data and remove it afterwards (the audit table is append-only and stays).
- **Access:** every route needs a role check. The general `tenant_member` dependency deliberately REFUSES `merchant_user`; merchant staff only reach
  `/tenants/{id}/portal/*`, which is scoped to one merchant. Only the workspace owner adds merchants. New routes must not leak across merchants or workspaces.
- **Admins:** platform administrators live in the database (`platformadmin`) plus the bootstrap list `ROUTEBRIDGE_PLATFORM_ADMIN_SUBJECTS` (a JSON list).
- **Fixed session time:** `NEXT_PUBLIC_SESSION_MAX_HOURS` (12) and `NEXT_PUBLIC_SESSION_IDLE_MINUTES` (30), enforced by `components/session-guard.tsx`.
- **Look (Oct 2026, cobalt):** cobalt `#1746D1` for actions and the current page (white text on it), deep navy `#0F172A` sidebar and banners, `#F8FAFC` page, white cards, `#E2E8F0` borders, `#64748B` secondary text; flat, no glow, gradients or pulsing. Set in the LAST block of `app/globals.css` ("Cobalt layer"; older layers above are left as they were). A few screens set colours inline (driver app, tracking page, claims, shop registration). Green = delivered/live, red = problems, amber = needs attention. The owner's photo is `public/routebridge-bg.jpg` (+ `-sm` for phones), used on the sign-in pages and in the dashboard banner only, never behind data. The 6 MB original in the project root is not committed.
- **Going live:** `docker-compose.yml` + `.env.example` + README "Going live". `ENVIRONMENT=production` makes the API refuse unsafe settings; check what it would refuse with `docker compose exec -T -e ROUTEBRIDGE_ENVIRONMENT=production api python -c "from routebridge.config.settings import get_settings; from routebridge.config.validation import production_problems; print(production_problems(get_settings()))"`.
- **.env gotcha:** Docker Compose reads `KEY=   # comment` (an EMPTY value followed by a comment) as the comment text. Never put comments on value lines in `.env*` files; use their own line above. `.env.production` (gitignored) holds the live Clerk keys for the server only: production Clerk keys do not work on localhost, so the local `.env` keeps the development keys.
- **SMS gateways:** `providers.HttpMessagingProvider` supports JSON gateways (Termii style) and Twilio (`SMS_AUTH_STYLE=basic`, `SMS_CONTENT_TYPE=form`, key written `SKsid:secret`). The owner's first Twilio key/secret pair was rejected by Twilio in every region (error 8001/70051); do not store unverified gateway credentials, they make the production check pass falsely.
- **Maps:** `MAP_PROVIDER` (osm | maptiler | mapbox) + `MAP_API_KEY`, built in `lib/map-source.ts`; baked in at build time.
- **Live tracking** (`services/tracking.py`, `components/live-map.tsx`): the driver app pings, the server keeps the latest position on the driver; customers see a rider only while their parcel is en route/arrived and the ping is under 15 minutes old.
- **Billing** (`config/plans.py`, `services/billing.py`, `routes/billing.py`): plans/prices are placeholders in code. Limits only apply when `BILLING_ENFORCED=true`; an ended plan blocks NEW riders/people/merchants/orders after a 7 day grace, never running deliveries. Paystack webhook is `/api/v1/webhooks/paystack` and must be registered before the generic `/webhooks/{provider}` route. Platform staff set plans via `PUT /platform/tenants/{id}/plan` (no console button yet).
- **Statements and claims** (`services/statements.py`, `routes/claims.py`): a merchant statement = cash collected - delivery fees (rate card) + approved merchant claims decided in the period. Claim flow open > investigating > approved|rejected, approved > paid; rejecting needs a reason shown to the shop; `internal_note` is staff only. Portal pages `/statements` and `/problems`; staff claims sit under Reconciliation.
- **Driver push alerts** (`services/push.py`, `lib/driver/push.ts`, `public/sw.js`): off until `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` are set (make the pair with `gen_secrets`). The OUTBOX worker sends the push when it publishes `delivery.assignment.created`, so the notification-worker/outbox-worker must be running and Redis configured. Never printed or committed: the private key. Monitoring (Prometheus/Alertmanager/Grafana) is the compose `monitoring` profile; config in `deploy/monitoring/`.
- **Proof tools** (all use throw-away databases, never the real data): `bash deploy/backup-restore-test.sh` (backup, restore, compare every table), `docker compose exec -T api python -m routebridge.tools.db_selfcheck` (migrations from empty + PostGIS). Launch tasks and what is verified: `docs/launch-checklist.md`. Compose rule: never mark a variable `:?required` for an OPTIONAL profile's service; compose validates every service, so it breaks every command on a server without that variable.
- **Live deployment (Oct 2026, no domain, no server):** this PC is the server. `web-demo` (docker-compose.demo.yml, port 3100, calls the API on its own address via a Next rewrite) is published by `tailscale funnel --bg 3100` at https://neche.taile59d7a.ts.net with the Clerk DEVELOPMENT keys. The `tunnel` container (temporary trycloudflare link) is stopped. The normal `web` on :3000 is unchanged. Real server path: `deploy/setup-server.sh` + `docs/deploy-without-a-domain.md`. SMS is off (`ALLOW_LOG_SMS`); the production Clerk instance needs a domain the owner does not have.
- **Adding people and shops** (`routes/admin.py`, `routes/governance.py`, `routes/merchant_profiles.py`, `models/merchant_profile.py`): members AND merchants are added only by the person's Clerk user id (a person signs up, sees their id on the "not linked yet" screen, sends it). Adding a merchant also creates its `merchant_user` login; the id cannot already be an active member. The shop then registers itself on its Overview (phone, address, bank account) via `PUT /portal/profile`; until `is_complete()` it cannot create orders (422). Details live in the separate `merchantprofile` table so bank data never rides on the `Merchant` rows other roles can list; `GET /merchant-profiles` shows bank fields only to owner/admin/finance. Riders get a `merchant` card (name, phone, address, never bank) in `GET /driver/.../jobs`. Merchants created before this (no login) still exist; link them with Members & roles. Removing a shop (`DELETE /admin/tenants/{t}/merchants/{m}`, owner only, Settings > Merchants > Remove) is a SOFT remove (`status=removed`): its logins go inactive, it drops out of lists, billing counts and new orders (409), history and statements stay; refused (409) while it has deliveries on the way. Its user id can be reused. Restore (`POST .../merchants/{m}/restore`, owner only; removed shops listed by `GET .../removed-merchants`; Settings > Merchants > Removed shops) sets it active and switches its inactive logins back on. Sign-up asks what the person will do (`components/signup-role.tsx`, `lib/signup-role.ts`; browser-only, only shapes the message they send the owner) and the "not linked yet" screen shows their id as a Shop sign-up ID or User ID (always the same Clerk id). The shop's own Shop ID (a UUID made when it is added) is shown with a copy button on the shop's dashboard and on the owner's Shop details cards.
- **Delivery code is the fraud check** (`routes/operations.py` `capture_proof`, `REQUIRE_DELIVERY_CODE`; code default off so old tests/flows pass, compose default `true`): when on, a delivery completes only after the server verified the customer's code (hashed, expiring, attempt-limited); a photo or signature alone gets 409. Wrong guesses record `delivery.code_wrong` (never the guess). `OrderRead.code_verified` / `PortalOrder.code_verified` show it to staff and shops; driver jobs carry `code_required`. Status changes reach staff over the live stream (plus a 20 s fallback poll in `app/page.tsx` when the stream is not live) and the shop portal polls every 10 s with toasts (`lib/status-updates.ts`). The last block of `globals.css` is the 'Polish layer'.
- **Running this PC as the server:** `deploy/windows/start-routebridge.ps1` (Docker Desktop + stack, no rebuild), `health-check.ps1` (read-only), `backup-now.ps1` (dump + verify, saved in `%USERPROFILE%\RouteBridgeBackups`, never in the repo). If Docker's engine hangs after a restart: quit Docker Desktop, `wsl --shutdown`, reopen. Website builds can take 10+ hours when memory is short: close other programs, build one container at a time. The sign-in page limits attempts (5 per 15 minutes), so repeated automated sign-ins lock you out for a while. `docs/user-guide.md` is the plain-language manual.
- **Roles (Oct 2026, simplified):** the owner IS the Admin (`tenant_owner`, one person, full control, the only one who adds people or shops). The only people added from Members & roles are **Dispatchers**: the `driver` role, a rider tied to a `Driver` record by `TenantMembership.driver_id` (phone + Staff/Contracted `fleet_type`), added by Clerk user id. `ASSIGNABLE_ROLES` in `models/access.py` limits what can be handed out; the older roles (tenant_admin, dispatcher, operations_manager, finance, ...) stay valid so existing logins keep working but cannot be given to anyone new. `tenant_member` refuses `driver` and `merchant_user`; a signed-in Dispatcher swaps their account for a rider-app token with `POST /driver/tenants/{t}/me/token`, and the console redirects them to `/driver#token=...`, which lists only their own assigned orders. **Staff never create orders:** `no_staff_orders` (authorization.py) refuses `POST /orders` and `/orders/import-csv` for any signed-in member; shops place orders through `/portal/orders` (which calls `create_order` in-process), and the Admin assigns a rider on the Dispatch board. Every shop order must carry `service_zone_id` (portal `GET /portal/zones` lists names only). Tests that need an order use `helpers.post_order` / `helpers.make_zone`. Names shown to people live in `lib/roles.ts`.
- **Registration and adding (Oct 2026, round 2):** there is no Members & roles tab any more. The Admin adds a **shop** in Settings > Merchants with only its Clerk user id (the placeholder name `PENDING_SHOP_NAME` is replaced when the shop types its own company name in `shop_name` on `PUT /portal/profile`, which is required while the placeholder is there) and a **Dispatcher** on the Dispatchers screen with only the user id plus Staff/Contracted (`POST /tenants/{t}/members`, role `driver`). A future Dispatcher first saves name, phone and picture with `PUT /auth/me/rider-registration` (stored on `User.phone/photo`, migration `f2a3b4c5d6e7`; email and password are Clerk's); adding them copies these onto a new `Driver` row, and 422 "has not registered yet" if missing. Orders show their arrival date and time (`arrivedAt` in `lib/jobs.ts`). UI wording is "Cash on delivery". The platform "Activity" tab (`GET /platform/audit?company=`) merges platform actions, every company's audit events with their facts, and new sign-ups, and refreshes every 15 s. The real workspace is now named "RouteBridge" (was JuraNova; new-workspace form defaults to it); its zones (Lagos, Abuja, Kano, Ibadan) were inserted straight into the real database. Zones are no longer added by the Admin: a shop picks or adds its own in registration (`POST /portal/zones`, `merchantprofile.service_zone_id`, migration `a3b4c5d6e7f8`); `POST /admin/tenants/{t}/zones` is platform-admin only. `DELETE /tenants/{t}/drivers/{id}` (owner) soft-removes a Dispatcher (`Driver.status="removed"`, login off, 409 while a delivery is on the way); adding the user id again brings them back.
- **Tracking-link space and evidence of delivery** (`services/order_extras.py`, `routes/order_extras.py`, portal twins under `/portal/orders/{id}/...`, `components/order-extras.tsx`): `GET .../orders/{id}/tracking-share` gives the customer's name and phone, the link, the ready text (template `tracking_link`) and what was already sent; `POST .../tracking-share/send?channel=sms|whatsapp` queues it (only recorded while `SMS_PROVIDER=log`, and the screen says so; "Send on WhatsApp now" opens wa.me with the text). `GET .../orders/{id}/evidence` returns who received it, when, whether the code was verified, cash, the photo and signature as something an `<img>` can show (a presigned link with S3, else the file inlined as a data URL up to 4 MB). Shops get the same for their own orders only, without the rider's name.
- **Delivery code reaches the customer three ways:** when the rider asks (`issue_delivery_otp`) the code is (1) shown on the customer's own tracking page (`delivery_code` in `GET /public/tracking/{token}`, `Cache-Control: no-store`, only while the job is en_route/arrived and the code is unused and unexpired; the page buzzes and, if allowed, notifies), (2) queued as an SMS and a WhatsApp text (only recorded while `SMS_PROVIDER=log`), and (3) with `OTP_DELIVERY=dashboard` also shown as a card to staff. `relay_code` is now kept until the code is used, replaced or expires (marking the card sent no longer erases it); the card API returns nothing unless the mode is `dashboard`. The rider never sees the code.
- **Shop plans and online payment** (`config/plans.py` `SHOP_PLANS`, `routes/portal_billing.py`, `services/billing.py` shop functions, `components/shop-billing.tsx`, migration `b4c5d6e7f8a9`): each SHOP has its own plan (Free trial 14 days, Basic, Standard, Pro; placeholder prices) in `merchantplan`, made on first use, and pays for it itself on its portal page `/billing` through Paystack (`/portal/billing`, `/checkout`, `/verify`; shop payments are `billingpayment` rows with `merchant_id`, settled by the same `settle()` and the same Paystack webhook). Payment is ENFORCED: when a shop's plan has ended (no grace) or its month's orders are used up, `POST /portal/orders` returns 402 until it pays; deliveries already on the road are never touched. It is only enforced while `SHOP_BILLING_ENFORCED` (default true) AND a Paystack key is set, so nobody is locked out when they cannot pay. The Admin has NO Plan & billing page of their own and cannot buy a plan: Settings > Shop subscriptions (`GET /tenants/{t}/billing/shops`) is read-only and shows what each shop subscribed to and when it expires. The company's own checkout/verify/summary endpoints were removed; platform staff still set a company's plan (`PUT /platform/tenants/{t}/plan`, Platform console), and company limits still follow `tenant.plan`. Online payment only works once `PAYSTACK_SECRET_KEY` is set (and, on a server, `PAYSTACK_CALLBACK_URL` = the site address, plus the webhook `<api>/api/v1/webhooks/paystack` registered in the Paystack dashboard). Shops that existed before get a trial starting the first time they place an order or open the page. The company's own plan (the Admin paying RouteBridge) is separate. The `/platform` endpoints work but are hidden from Swagger (`include_in_schema=False`). Driver photos are no longer set from the console (those two routes were removed); a Dispatcher's picture comes from their own registration.
- **Automatic assignment** (`services/dispatch.py`) is off per workspace until switched on; it never picks a busy or offline driver.
- **Dispatcher zones** (`services/driver_zones.py`, `driverzone` table, migration `d6e7f8a9b0c1`): a rider types the areas they deliver in at registration (`zones` on `PUT /auth/me/rider-registration`, kept as text on `User.rider_zones`, required); when the Admin adds them, names matching the company's zones (any case) become their zones. The Admin changes them on the Dispatchers screen (`PUT /tenants/{t}/drivers/{id}/zones`, owner/admin). Rule everywhere: a job with no zone, or a rider with NO zones set, always matches; otherwise the job's zone (`JobPlan.service_zone_id`) must be one of the rider's. Manual and batch assignment return 409 outside it; automatic assignment only considers matching riders (`no_driver_in_zone`). Rate cards also take a `cod_fee` from the console form. The shop's New order form makes it pick the CUSTOMER's zone every time (never pre-filled with the shop's own zone), since that zone picks the riders and the rate.

## Known limits
SMS and WhatsApp are `log` only until a sender ID is registered. Real vendors, PostGIS and Clerk webhook delivery are untested.
The driver app is a PWA, not native. Privacy documents are drafts needing legal review.
